# Retries and backoff

Naive retry logic is one of the great outage amplifiers. A
downstream blip turns into a retry storm, the downstream stays
down longer, and now the dependency *of* the downstream is also
having a day. Retries done well make systems robust; done
carelessly, they spread failure.

## Retry only what's retryable

- **Retry**: transient network errors (connection reset, DNS
  blip), 5xx without a clear "do not retry" signal, 429 with
  `Retry-After`, timeouts on a known-idempotent operation.
- **Don't retry**: 4xx other than 408 / 425 / 429, validation
  failures, auth failures (rotate creds; don't pound), any error
  the provider explicitly marks non-retryable.

Wrong-bucket retries are an attack on your own backend.

## Exponential backoff with jitter

- Backoff: `base * 2^attempt`, capped at a max.
- Jitter: full or "decorrelated" jitter. Never fixed backoff
  across many clients — they synchronize and stampede.
- A reasonable default: `base=100ms`, `cap=30s`,
  `max_attempts=5`, with full jitter.

```
delay = random_between(0, min(cap, base * 2^attempt))
```

## Attempt cap and total budget

Bound *both*:

- Max attempts (e.g., 5).
- Max total wall clock (e.g., 30s).

Whichever fires first stops the retry loop. Unbounded retries are
how a single bad request consumes a worker forever.

## Idempotency

You can only safely retry an operation that is idempotent. For
operations that are not naturally idempotent (create, charge,
send), include an **idempotency key**:

- Generated by the caller, deterministic per logical operation.
- Sent on every retry of that operation.
- Honored by the server — same key returns the original result
  rather than executing twice.

If you cannot supply an idempotency key, retrying mutating
operations is a bug; surface the failure to the caller.

## Honor server signals

- `Retry-After` (seconds or date) — wait at least that long.
- 429 with no `Retry-After` — backoff, but back off harder than
  for transient 5xx.
- Token-bucket headers (`X-RateLimit-*`) — adjust outgoing rate
  preemptively.

Ignoring these headers means you're not rate-limited; you're
banned.

## Circuit breakers

When a downstream is failing persistently, stop calling it for a
while:

- Track failure rate over a sliding window.
- Open the circuit on threshold; fail fast for callers.
- Half-open after a cool-down; one probe; close on success.

Without a breaker, retry loops keep the downstream pinned even
after it tries to recover.

## End-to-end retries are the worst

A retry at every layer multiplies: 3 × 3 × 3 = 27 attempts for
one user click. Pick **one** layer to retry at — usually the
closest to the dependency — and disable retries above it. Always
document which layer owns retries for which dependency.

## Anti-patterns

- Retry on all errors, including 400. Now invalid input gets
  retried until the user gives up.
- Fixed-delay retries. All your clients fire at the same moment.
- Retrying without an idempotency key on a `POST /charge`.
- A retry loop inside a retry loop inside a retry loop.
- Increasing `max_attempts` to fix flakiness. The downstream is
  flaky; you're masking it. Fix or alert.
- Retry that keeps the connection / lock / transaction open
  across all attempts. One slow downstream blocks everyone.
